# RULES — правила, договорённости, ритуал переделок

Один документ, чтобы правила не жили в переписке и памяти. Здесь позиция публичного слоя, процесс правок, чек-лист переделки и уроки сессий. Порядок силы прежний: указание владельца сильнее этого документа, этот документ сильнее привычек.

Источники: решения владельца 07.11–09.11.2026 (журнал в PROJECT-META), журнал сессий (SESSIONS). Документ живой: новое решение добавляется сюда в день принятия.

## 1. Позиция: публичный слой

1.1. С публичных страниц только продукт, не кухня. Коммиты, страницы, строки, часы не аргумент для тех, кто их не прожил. Метрики контента карты (31 версия, 74 героя, 222 предмета, 408 стадий ИИ) показывать можно: игрок проверяет их на самом сайте.
1.2. Ссылок на github.com в публичном HTML ноль. После чисток проверять поиском.
1.3. href=# без адресов: support.html 7 кнопок, info.html 2. Оставлены намеренно, реальные адреса знает и вносит сам владелец. Не трогать и не выдумывать адреса.
1.4. Тон метафайлов: система, которая держит темп, работа сильного одиночки на длинной дистанции. Без самоиронии, без исповедальности.
1.5. Данные карты не выдумываются. Если сайт расходится с картой, правду узнают пересчётом в редакторе, до тех пор расхождение помечается, не чинится.

## 2. Процесс правок

2.1. Мелкие чанки: одна задача, один коммит, один пуш. История читается как журнал работы.
2.2. Сообщение коммита: одна строка, строчными, по-человечески, без тире, стрелок, точек с запятой и служебных префиксов. Отчёты о проверках в сообщение не тянутся.
2.3. Массовые правки HTML и CSS делаются идемпотентными node-скриптами из scripts/tmp/ (вне git): проверка includes перед вставкой, маркеры, откат git checkout -- между итерациями, проверка корня репозитория в начале скрипта. Постоянные проверки живут в scripts/ и попадают в CI.
2.4. Гейты до каждого коммита, а не после: check-links, check-text, check-header-sync, check-counters. Четыре зелёных, потом пуш.
2.5. Аудит-отчёт сайт не трогает: это снимок. Правки по отчёту отдельным чанком и по решению владельца.
2.6. Механизм «отключить мёртвое правило с резервом» закрыт 08.11: метрика «класс не используется» обманула 69 раз из 69. Ничего не отключать без отдельного решения владельца и скринов до и после.
2.7. Файлы не удалять, переносить в repo-archive/.
2.8. Правка истории git точечная: только согласованные сообщения, имена и мёртвые блобы, перед прогоном бэкап всей истории.
2.9. Локальные папки владельца (HeroData/, archive/) не трогают ни пуши, ни правка истории, ни git reset --hard.
2.10. Токены и секреты в репозиторий не попадают никогда, включая документацию и журналы.

## 3. Ритуал переделки: что менять и править

Перед правкой страницы:
- инвентаризация страницы целиком, контент переносится дословно;
- шапка: эталон info.html, раскатка и проверка check-header-sync;
- футер: раскатка place-footer.py;
- canonical, JSON-LD и мета-описание меняются вместе со смыслом текста.

При правке css/*.css:
- после любого css-файла пересобирать бандл: python3 scripts/build-css-bundle.py;
- новый цвет или токен сначала в css и DESIGN.md, потом в разметку, ничего «примерно такого же»;
- палитра только через var() из :root, литералы обратно не возвращать;
- радиусы, тени, ширины, z-index по DESIGN.md, новые значения фиксируются там же;
- перегенерировать scripts/audit-inline-css.mjs при работе с хардкодом стилей: сверка с палитрой идёт до правок и после.

При новой странице:
- sitemap.xml через gen-sitemap.py, JSON-LD, canonical;
- новый скрипт записывается в JS-MAP.md, карта перегенерируется gen-js-map.py.

При витринных числах:
- единственный источник site-counters.js, гейт check-counters.py, в текстах числа меняются вместе с ним.

Формулировки в документах и журналах:
- писать с учётом триггеров собственного check-text (список в шапке скрипта): словоформы ловятся не все, сомнительные обороты сразу заменять безопасными.

После любой правки:
- браузером: консоль чиста, 1280 и 390 px без горизонтального скролла;
- гейты, затем коммит и пуш.

## 4. Как не работать вслепую

Отдельное правило после длинной охоты за одной строкой в генераторе отчёта:

4.1. Если проблема не локализуется за два хода, проблемный кусок переписывается заново простым способом. Слепой перебор дольше пары проверок запрещён.
4.2. Синтаксис проверяется до запуска: node --check для js, python3 -m py_compile для python. Секунда проверки экономит полчаса.
4.3. В генераторах отчётов и массовых правках не использовать вложенные шаблонные литералы: конкатенация обычных строк там, где в шаблон нужны кавычки или бэктики.
4.4. Любой чекер обязан печатать число прошедших проверку, а не только число ошибок: пустой отчёт неотличим от сломанного.

## 5. Уроки сессий 07.11–09.11

- Гейты до коммита: один чанк ушёл без прогона, следующему пришлось чинить журнал.
- Чекер, который не печатает число прошедших фильтр ссылок, ничего не проверяет: первый check-items показывал 2637 битых ноль при нуле же проверенных.
- «Класс не используется» лживая метрика: 69 ложных отключений из 69, поломанные шапка и лавка, восстановление реконструкцией из состояния до коммита со сверкой computed по контрольным точкам.
- Массовая замена требует построчного трекинга комментариев: файловый флаг «changed» съедал закрывашки /* */, и комментарии глотали живые правила.
- Маркер по иконке искать от позиции иконки через lastIndexOf открытого тега: у иконок бывают составные классы.
- Sync-кнопка слипает несвязанные истории: второй клон синхронится через git fetch и git reset --hard origin/main.
- Всё долговременное живёт только в репозитории: локальный метафайл с правилами погиб вместе с игнором при пересборке окружения, этот документ и есть ответ на тот урок.
- После восстановления окружения: переклонировать репозиторий, git config core.fileMode false, восстановить авторство коммитов, перегнать гейты до первой правки.
- Автоматизация текстов имеет границы: тире в лоре оставлено сознательно, это риторика художественного текста, а не мусор.
- Снимок и решение: сначала аудит-отчёт, потом решение владельца, потом отдельный чанк правок. Ни один аудит не кончился правкой без решения.
